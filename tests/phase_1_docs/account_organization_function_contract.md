# ARK account, organization, and business function contract

Contract version: `0.1.0`

This document defines the application-service boundary shared by developers
implementing ARK Phase 1 account, organization, membership, authorization,
API-key, business, session, verification, and audit behavior. It specifies
function names, inputs, expected outputs, authorization, state effects, and error
codes. It contains no implementation bodies and does not prescribe controllers,
HTTP routes, frameworks, or database repositories.

| Domain | Functions |
|---|---|
| User/authentication | `register_user`, `login_user`, `refresh_session`, `logout_user`, `logout_all_sessions`, `request_user_verification`, `confirm_user_verification`, `edit_user`, `get_user`, `delete_user` |
| Organization | `add_organization`, `edit_organization`, `get_organization`, `list_organizations`, `suspend_organization`, `reactivate_organization`, `delete_organization`, `get_organization_capability_pattern`, `update_organization_capability_pattern` |

| Audit | `list_audit_events`, `get_audit_event` |

## 1. Scope and ownership

| Area | Owns | Does not own |
|---|---|---|
| User | Human profile and lifecycle state | Organization membership or permissions |
| Authentication | Session and verification challenge contracts | Raw proof persistence or provider selection |
| Organization | Organization lifecycle, administration, and one versioned capability pattern | Business data or capability execution |
| Member | User-to-Organization relationship, one selected Role, and Role-limited reach to every Organization Business | Role/Permission definitions or per-Business assignments |
| API key | One current key per active Member and rotation lineage | Member authorization or Role contents |
| Authorization catalog | System-managed, versioned Roles and Permissions | Organization-defined Roles or Permissions |
| Business | Business lifecycle and Organization parent | Organization capability-pattern definition |
| Audit | Immutable actor/action/target/result evidence | Authentication or authorization decisions |

## 2. Contract-wide invariants

1. IDs are opaque contract types. Their physical representation may be UUID,
   bigint, or another approved database type without changing this contract.
2. Caller-supplied IDs are lookup values only. Trusted User, Member,
   Organization, and Business scope comes from `RequestContext` and stored
   relationships.
3. A Member belongs to exactly one Organization, references one User, has exactly
   one selected Role, and is unique by `(user_id, organization_id)`. The same User
   may join multiple Organizations, but only once per Organization. An active
   Member can address every current and future Business in that Organization
   subject to the Role's Permissions.
4. There are no per-Business Member grants, assignments, allowlists, or
   exceptions. Business reach is derived through the Organization relationship.
5. Every active Member has exactly one current active API key. Revoked
   predecessors MAY remain only for rotation and audit history.
6. Roles, Permissions, and Role-to-Permission mappings are system-managed and
   versioned. Organization owners may select them but MUST NOT mutate them.
7. A Business belongs to exactly one Organization. `organization_id` cannot be
   changed by an edit operation.
8. Business operations always resolve exactly one Business tenant. Organization-
   wide reach does not imply cross-Business aggregation, combined datasets,
   bulk export, or unscoped data access.
9. Each Organization has one versioned capability pattern that applies uniformly
   to all current and future Businesses. Per-Business capability overrides are
   prohibited.
10. `delete_*` functions perform logical lifecycle transitions. They MUST NOT
   physically erase audit, billing, job, usage, or result history.
11. Every mutation requires an idempotency key and emits immutable audit evidence.
12. Every edit or lifecycle transition requires `expected_version`. A stale
    version fails without mutation.
13. Timestamps and versions are generated by the authoritative service, never
    trusted from client input.
14. Raw API keys, access tokens, refresh tokens, authentication assertions, and
    verification codes are write-only or one-time output values. They MUST NOT be
    logged or returned again.
15. A high-impact mutation fails closed if mandatory audit persistence is
    unavailable.

## 3. Function notation

Every function follows this abstract contract:

`function_name(RequestContext, FunctionInput) -> OperationResult<FunctionOutput>`

This notation is a boundary signature only. It is not executable code and does
not imply a programming language.

### 3.1 RequestContext

| Field | Type | Required | Contract |
|---|---|---:|---|
| `request_id` | `RequestId` | Yes | Unique correlation ID for one request |
| `idempotency_key` | `IdempotencyKey` | Mutations | Same key plus same fingerprint returns the original result |
| `actor_type` | `USER \| API_KEY \| SYSTEM \| ANONYMOUS` | Yes | Trusted actor class |
| `actor_id` | `ActorId` | Except anonymous | Stable actor identifier |
| `user_id` | `UserId?` | Contextual | Authenticated User when known |
| `session_id` | `SessionId?` | User session calls | Current session |
| `member_id` | `MemberId?` | Organization-scoped calls | Active Member used for authorization |
| `organization_id` | `OrganizationId?` | Organization-scoped calls | Derived Organization scope |
| `business_id` | `BusinessId?` | Business-scoped calls | Derived Business tenant scope |
| `role_id` | `RoleId?` | Member calls | Selected Role snapshot |
| `role_version` | `Version?` | Member calls | Role version used for the decision |
| `authenticated_at` | `Instant?` | Authenticated calls | Time authentication was established |

Application callers MUST NOT construct trusted actor fields themselves. An edge
adapter or trusted internal scheduler creates this context. (the client is not allowed to tell ARK who they are.)
Instead, the client sends its authentication proof (APIKEY)

### 3.2 OperationResult

| Field | Type | Required | Contract |
|---|---|---:|---|
| `request_id` | `RequestId` | Yes | Echoes the request correlation ID |
| `data` | Operation output | On success | Exact output defined by the function |
| `audit_event_id` | `AuditEventId?` | Mutations | Audit event associated with the effect |
| `resource_version` | `Version?` | Resource mutation | Version after the effect |
| `replayed` | `boolean` | Yes | True when returned from a matching idempotent replay |
| `error` | `ContractError?` | On failure | Structured failure; no partial success is hidden |

### 3.3 ContractError

| Field | Type | Required | Contract |
|---|---|---:|---|
| `code` | `ErrorCode` | Yes | Stable machine-readable code |
| `message` | `string` | Yes | Safe human-readable summary |
| `field_errors` | `map<string,string>` | No | Input validation details |
| `current_version` | `Version` | Version conflict | Current resource version |
| `retryable` | `boolean` | Yes | Whether an unchanged retry can succeed |
| `request_id` | `RequestId` | Yes | Correlation ID |

Errors MUST NOT disclose raw keys, tokens, verification codes, hashes, User
existence during login, or resources outside the actor's authorized scope.

### 3.4 Shared scalar types

| Type | Meaning |
|---|---|
| `Instant` | UTC timestamp with timezone |
| `Version` | Positive optimistic-concurrency version |
| `PageSize` | Integer from 1 through 100 |
| `PageToken` | Opaque continuation token |
| `Status` | Resource-specific lifecycle status |
| `SecretOnce` | Sensitive value returned once and never retrievable |

## 5. Authorization permission codes

These codes are the function-level authorization contract. Role definitions map
to these codes but remain system-managed.

| Permission | Allows |
|---|---|
| `organization.create` | Create an Organization for the authenticated User |
| `organization.read` | View and list an authorized Organization |
| `organization.manage` | Edit, suspend, reactivate, or close an Organization |
| `capability_pattern.read` | Read the Organization's enabled-capability pattern |
| `capability_pattern.manage` | Replace the Organization's enabled-capability pattern |
| `members.read` | View and list Members |
| `members.manage` | Add, edit, suspend, reactivate, or remove Members |
| `members.role.assign` | Select a system-managed Role for a Member |
| `api_keys.read` | Read non-secret API-key metadata |
| `api_keys.rotate` | Rotate or revoke the Member's current API key |
| `authorization.read` | List and get Roles and Permissions |
| `business.read` | View and list Businesses |
| `business.manage` | Add, edit, suspend, reactivate, or close Businesses |
| `audit.read` | Read Organization-scoped audit events |

Self-service User profile, login, logout, and verification functions use User
ownership rules rather than Organization permissions.

Every Organization-scoped Business permission applies uniformly to all
Businesses belonging to the trusted Organization context. Permission codes never
carry or imply a selected-Business allowlist.

## 6. User and authentication functions

### 6.1 `register_user`

Signature: `register_user(RequestContext, RegisterUserInput) -> OperationResult<RegisterUserOutput>`

Authorization: anonymous registration policy or trusted administrative bootstrap.

| Input field | Type | Required | Validation |
|---|---|---:|---|
| `full_name` | `string` | Yes | Trimmed length 1–200 |
| `phone` | `string` | Yes | E.164 format |
| `email` | `string` | No | Normalized valid address, maximum 320 |
| `city_id` | `string` | No | Approved city code |
| `terms_version` | `string` | Policy-dependent | Must equal an accepted active version |

| Output field | Type | Contract |
|---|---|---|
| `user` | `UserView` | New `ACTIVE` User |
| `verification_required` | `boolean` | Whether confirmation is required before login or organization creation |
| `allowed_verification_channels` | `string[]` | Channels supported by the active trust profile |

Effects: creates only the User profile. It does not create an Organization,
Member, Role, API key, or session.

Errors: `VALIDATION_FAILED`, `USER_ALREADY_EXISTS`, `REGISTRATION_DISABLED`,
`TERMS_NOT_ACCEPTED`, `AUDIT_UNAVAILABLE`.

### 6.2 `login_user`

Signature: `login_user(RequestContext, LoginUserInput) -> OperationResult<LoginUserOutput>`

Authorization: anonymous. The selected trust adapter validates the proof.

| Input field | Type | Required | Validation |
|---|---|---:|---|
| `trust_profile_id` | `string` | Yes | Approved active trust profile |
| `identifier` | `string` | Yes | Normalized by the selected profile |
| `authentication_assertion` | `SecretOnce` | Yes | Write-only; never logged or persisted as plaintext |
| `requested_session_ttl_seconds` | `integer` | No | Must not exceed policy maximum |

| Output field | Type | Contract |
|---|---|---|
| `session` | `SessionIssuedView` | New session and one-time token material |
| `user` | `UserView` | Authenticated User |
| `organizations` | `OrganizationView[]` | Optional bounded bootstrap summary; not authority |

Errors: `AUTHENTICATION_FAILED`, `USER_NOT_ACTIVE`, `VERIFICATION_REQUIRED`,
`TRUST_PROFILE_UNAVAILABLE`, `RATE_LIMITED`, `AUDIT_UNAVAILABLE`.

`AUTHENTICATION_FAILED` MUST be indistinguishable for unknown identifiers and
invalid assertions.

### 6.3 `refresh_session`

Signature: `refresh_session(RequestContext, RefreshSessionInput) -> OperationResult<RefreshSessionOutput>`

Authorization: valid refresh material under the session policy.

| Input field | Type | Required |
|---|---|---:|
| `session_id` | `SessionId` | Yes |
| `refresh_token` | `SecretOnce` | Yes |

| Output field | Type | Contract |
|---|---|---|
| `session` | `SessionIssuedView` | Rotated session token material |

Effects: invalidates the presented refresh material and returns its successor.

Errors: `SESSION_NOT_FOUND`, `SESSION_EXPIRED`, `SESSION_REVOKED`,
`AUTHENTICATION_FAILED`, `RATE_LIMITED`.

### 6.4 `logout_user`

Signature: `logout_user(RequestContext, LogoutUserInput) -> OperationResult<LogoutUserOutput>`

| Input field | Type | Required |
|---|---|---:|

Effects: revokes the specified session and all of its refresh material.

Errors: `FORBIDDEN`, `AUDIT_UNAVAILABLE`. A missing or already revoked owned

### 6.10 `delete_user`

Signature: `delete_user(RequestContext, DeleteUserInput) -> OperationResult<DeleteUserOutput>`

Authorization: User self-service with required stronger authentication, or
approved security administration.

| Input field | Type | Required |
|---|---|---:|
| `user_id` | `UserId` | Yes |
| `expected_version` | `Version` | Yes |
| `reason` | `string` | Yes; length 1–500 |

| Output field | Type |
|---|---|

policy-driven process.

Errors: `USER_NOT_FOUND`, `FORBIDDEN`, `VERSION_CONFLICT`,
`LAST_ORGANIZATION_OWNER`, `AUDIT_UNAVAILABLE`.

## 7. Organization functions

### 7.1 `add_organization`

Signature: `add_organization(RequestContext, AddOrganizationInput) -> OperationResult<AddOrganizationOutput>`

Authorization: verified active User allowed by the platform-level Organization
creation policy. `organization.create` is a User/platform permission because no
Organization Member exists yet.

| Input field | Type | Required | Validation |
|---|---|---:|---|
| `name` | `string` | Yes | Trimmed length 1–200 |
| `owner_api_key_name` | `string` | Yes | Trimmed length 1–200 |
| `owner_api_key_expires_at` | `Instant` | Yes | Future time allowed by policy |

| Output field | Type | Contract |
|---|---|---|
| `organization` | `OrganizationView` | New active Organization |
| `owner_member` | `MemberView` | New active Member with `ORG_OWNER` Role |
| `owner_api_key` | `APIKeyIssuedView` | Member's one current API key; raw value returned once |

Effects are atomic: Organization, owner Member, first API key, and audit evidence
either all commit or none commit.

Errors: `USER_NOT_ACTIVE`, `VERIFICATION_REQUIRED`, `ROLE_NOT_AVAILABLE`,
`VALIDATION_FAILED`, `IDEMPOTENCY_CONFLICT`, `AUDIT_UNAVAILABLE`.

### 7.2 `edit_organization`

| Input field | Type | Required |

### 7.5 `suspend_organization`

Signature: `suspend_organization(RequestContext, SuspendOrganizationInput) -> OperationResult<SuspendOrganizationOutput>`

Authorization: `organization.manage`; stronger or platform authority MAY be
required by policy.

Input: `organization_id`, `expected_version`, and nonblank `reason`.

Output: updated `organization` with `SUSPENDED` status and `suspended_at` in the
operation result metadata.

Effects: denies new business ingestion and execution for every Business in the
Organization. Existing work follows the approved cancellation policy.

Errors: `ORGANIZATION_NOT_FOUND`, `INVALID_STATE_TRANSITION`, `FORBIDDEN`,
`VERSION_CONFLICT`, `AUDIT_UNAVAILABLE`.

### 7.6 `reactivate_organization`

Signature: `reactivate_organization(RequestContext, ReactivateOrganizationInput) -> OperationResult<ReactivateOrganizationOutput>`

Authorization: `organization.manage` plus any policy authority that imposed the
suspension.

Input: `organization_id`, `expected_version`, and nonblank `reason`.

Output: updated `organization` with `ACTIVE` status.

Reactivation restores eligibility checks; it does not activate blocked
capabilities or automatically reactivate closed/suspended Businesses.

Errors: `ORGANIZATION_NOT_FOUND`, `INVALID_STATE_TRANSITION`, `FORBIDDEN`,
`VERSION_CONFLICT`, `AUDIT_UNAVAILABLE`.

### 7.7 `delete_organization`

Signature: `delete_organization(RequestContext, DeleteOrganizationInput) -> OperationResult<DeleteOrganizationOutput>`

Authorization: active `ORG_OWNER` with `organization.manage` and required stronger
authentication.

Input: `organization_id`, `expected_version`, and nonblank `reason`.

Output: updated `organization` with `CLOSED` status and `closed_at` metadata.

Preconditions: all Businesses are closed or the close policy explicitly closes

## 12. State-transition summary

| Resource | Allowed transitions |
|---|---|
| User | `ACTIVE -> SUSPENDED -> ACTIVE`; `ACTIVE/SUSPENDED -> CLOSED` |
| Organization | `ACTIVE -> SUSPENDED -> ACTIVE`; `ACTIVE/SUSPENDED -> CLOSED` |
| Member | `ACTIVE -> SUSPENDED -> ACTIVE`; `ACTIVE/SUSPENDED -> REVOKED` |
| API key | `active -> revoked`; replacement creates a new active successor |
| Business | `ACTIVE -> SUSPENDED -> ACTIVE`; `ACTIVE/SUSPENDED -> CLOSED` |
| Role/Permission version | `ACTIVE -> RETIRED`; never reactivated in place |
| Session | `ACTIVE -> EXPIRED/REVOKED`; never reactivated |
| Verification challenge | `PENDING -> CONSUMED/EXPIRED`; never reused |

Any transition absent from this table returns `INVALID_STATE_TRANSITION` without
mutation.

## 13. Idempotency and concurrency

1. Creates and mutations MUST persist an operation fingerprint with the
   idempotency key within the authoritative transaction.
2. Reusing a key with the same canonical input returns the original output with
   `replayed = true`.
3. Reusing a key with different canonical input returns `IDEMPOTENCY_CONFLICT`.
4. Secret-bearing replay responses MUST NOT return the original raw API key or
   token again. Instead they return metadata plus `SECRET_ALREADY_DELIVERED` and
   require a rotation/recovery flow.
5. `expected_version` mismatch returns `VERSION_CONFLICT` and `current_version`.
6. List functions use stable ordering plus opaque continuation tokens.
7. The database constraint and service behavior for Member and API-key uniqueness
   must remain correct under concurrent calls, not only under sequential tests.

## 14. Audit requirements

Every mutation records at least:

| Field | Contract |
|---|---|
| `actor_type`, `actor_id` | Trusted actor identity |
| `organization_id`, `member_id`, `business_id` | Applicable derived scope |
| `action` | Stable function/effect code |
| `target_type`, `target_id` | Mutated resource |
| `result` | `SUCCESS`, `ACCEPTED`, `DENIED`, or `FAILED` |
| `request_id` | Correlation ID |
| `before_version`, `after_version` | Mutation lineage when applicable |
| `reason` | Required lifecycle/privileged-action reason |
| `occurred_at` | Server timestamp |

Raw secrets, hashes, authentication assertions, verification codes, tokens, and
unredacted sensitive profile values MUST NOT enter audit details.

## 16. Acceptance tests shared by both developers

The contract is not implemented until both sides pass these behavior tests:

1. Same idempotency key and same create input returns the same resource ID.
2. Same idempotency key with different input returns `IDEMPOTENCY_CONFLICT`.
3. Stale `expected_version` produces no mutation.
4. Forged Organization or Business IDs do not broaden the trusted context.
5. Adding a Member atomically creates exactly one active API key.
6. Concurrent Member additions cannot create duplicate rows for the same User and
   Organization; the losing request returns `MEMBER_ALREADY_EXISTS`.
7. Concurrent rotations cannot create two active API keys for one Member.
8. API-key replay never returns raw key material twice.
9. Suspending a Member immediately makes its API key unusable.
10. Reactivating a Member with no valid key atomically creates exactly one new key.
11. Role changes use only active system-managed Role versions.
12. The last active `ORG_OWNER` cannot be demoted, suspended, removed, or deleted.
13. A Business ID from another Organization is rejected without revealing its
    existence.
14. Suspending or closing a Business rejects new ingestion and execution.
15. Closing a User, Organization, Member, or Business preserves required history.
16. Audit-unavailable tests fail closed for every mandatory audited mutation.
17. Login errors do not reveal whether a User identifier exists.
18. Verification challenges are single-use, expire, and are rate-limited.
19. Pagination is stable and never returns out-of-scope resources.
20. No log, error, audit event, or repeated response contains a raw API key,
    token, verification code, or authentication assertion.
21. A Member with `business.read` can view every current Business in the Member's
    Organization and none in another Organization.
22. A Business created after the Member joined is automatically reachable under
    the same Role Permissions without a Member-Business grant.
23. A Role without `business.read`, `data.read`, or another requested action is
    denied that action across every Business despite Organization membership.
24. Every Business data/execution request contains one explicit Business and
    cannot use Organization-wide reach for unscoped or combined data access.
25. Updating the Organization capability pattern applies the same versioned set
    to every current and future Business.
26. Inputs containing a per-Business capability override or selected-Business
    list are rejected with `VALIDATION_FAILED`.
27. Enabling a capability in the Organization pattern does not bypass readiness,
    Role, quota, scientific, model, environment, security, or production blocks.

## 17. Critical unresolved decisions

The two developers MUST NOT independently invent different answers for these
items. They require an approved contract revision:

1. Human trust provider, assertion format, session-token format, lifetimes, and
   recovery process.
2. Whether phone is globally unique, reusable after closure, or only verified per
   User.
3. Exact Business Type catalog and whether it is an enum or system-managed table.
4. Exact Organization/Business close policy for in-flight jobs and reservations.
5. PII retention, redaction, deletion, and legal-hold policy.
6. Business transfer between Organizations. It is currently prohibited.
7. Stronger-authentication requirements for ownership, Role, API-key, and closure
   operations.
8. Concrete permission-to-Role mappings and activation authority.

## 18. Change-control rule

Any breaking change to a function name, required input, output meaning, state
transition, permission, error code, idempotency rule, or secret-handling rule
requires:

1. a contract-version increment;
2. review by both developers;
3. compatibility-test updates;
4. migration notes for callers and persisted state; and
5. architecture reconciliation when the change affects an accepted ARK decision.
