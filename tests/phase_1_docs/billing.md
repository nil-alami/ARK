# Billing module


# 1. Simple mental model

Billing has two main jobs.

### Job A: Manage Ark Credit

Each user has one Ark Credit wallet. The wallet belongs to the user, not to an organization.\ 
User’s organizations consume from the same wallet. However, every reservation records which organization caused the cost. 
```Text
User
  └── one shared credit wallet
        ├── available credits
        └── reserved credits
```


### ▶ Usage
### ▶ Credit packages


# 3. Database tables

All Billing tables live in the PostgreSQL `billing` schema.
There are **8 tables**, plus one shared sequence and one package-locking database function.

## 3.1 `billing.credit_accounts`

The current wallet balance for each user.

| Field | Meaning |
| ------------------- | ------------------------------------ |
| `user_id`           | Wallet owner and primary key         |
| `available_credits` | Credits available to spend           |
| `reserved_credits`  | Credits held for active operations   |
| `version`           | Increases after every balance change |
| `created_at`        | Wallet creation time                 |
| `updated_at`        | Last balance-change time             |

Important rules:

- There can be only one account per user.
- Available and reserved balances cannot be negative.
- The combined balance cannot exceed JavaScript’s safe integer maximum.
- `user_id` is not a foreign key to the Account module. Billing treats it as an external identity.

A missing account is presented by the API as a zero balance, even though no row exists yet.


### PostgreSQL SQL — reconstructed from this document

```sql
CREATE SCHEMA IF NOT EXISTS billing;

CREATE TABLE billing.credit_accounts (
    user_id BIGINT PRIMARY KEY,
    available_credits BIGINT NOT NULL DEFAULT 0,
    reserved_credits BIGINT NOT NULL DEFAULT 0,
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT credit_accounts_available_nonnegative
        CHECK (available_credits >= 0),
    CONSTRAINT credit_accounts_reserved_nonnegative
        CHECK (reserved_credits >= 0),
    CONSTRAINT credit_accounts_version_nonnegative
        CHECK (version >= 0),
    CONSTRAINT credit_accounts_js_safe_integer_limit
        CHECK (
            available_credits <= 9007199254740991 - reserved_credits
        )
);

-- Intentionally NO foreign key from user_id into the Account module.
```

`BIGINT` is used here as a reconstruction because the document does not state the exact SQL type of `user_id`.

## 3.2 `billing.credit_packages`

The credit packages customers may purchase.

| Field | Meaning |
| -------------------------- | ------------------------------------------- |
| `id`                       | Package ID                                  |
| `code`                     | Stable code such as `credit-100`            |
| `credits`                  | Credits granted after payment               |
| `amount_rials`             | Price in rials                              |
| `is_active`                | Whether customers can currently purchase it |
| `sort_order`               | Display order                               |
| `created_at`, `updated_at` | Audit timestamps                            |

Initial seeded packages:

| Code | Credits | Price |
| ---------------- | ----- | --------------- |
| `credit-100`     | 100   | 1,000,000 rials |
| `credit-250`     | 250   | 2,000,000 rials |
| `credit-1000`    | 1,000 | 7,500,000 rials |

The client sends only the package ID. It cannot submit its own number of credits or price.

When a payment order is created, the current package credits and price are copied into the order. Changing the package later does not rewrite historical purchases.

There is no package administration HTTP API. Packages currently need database/migration-level management.

## 3.4 `billing.credit_reservations`

A temporary hold for an operation whose final cost is not known in advance.

| Field | Meaning |
| -------------------------- | --------------------------------------- |
| `id`                       | Reservation ID                          |
| `payer_user_id`            | User whose wallet is held               |
| `organization_id`          | Organization that caused the operation  |
| `reserved_credits`         | Maximum reserved cost                   |
| `reference_id`             | Caller-provided operation/job reference |
| `expires_at`               | Server-calculated expiration            |
| `status`                   | Current lifecycle state                 |
| `settled_credits`          | Actual cost after settlement            |
| `created_at`, `updated_at` | Audit timestamps                        |

States:

```
active → settled
       → released
       → expired
```

All three final states are terminal.

The payer is determined when the reservation is created. If organization ownership changes later, the existing reservation still uses its original payer.

`payer_user_id` has a foreign key to `credit_accounts`. `organization_id` deliberately has no foreign key into another module.


### PostgreSQL SQL — reconstructed from this document

```sql

    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
```

## 3.5 `billing.credit_transactions`

The immutable accounting ledger.

| Field | Meaning |
| ------------------ | --------------------------------------- |
| `id`               | Ledger row ID                           |
| `user_id`          | Wallet affected                         |
| `transaction_type` | Reason for the balance change           |
| `available_delta`  | Change to available credits             |
| `reserved_delta`   | Change to reserved credits              |
| `available_after`  | Available balance after the transaction |
| `reserved_after`   | Reserved balance after the transaction  |
| `reference_type`   | Type of related entity                  |
| `reference_id`     | Related entity’s external/string ID     |
| `payment_order_id` | Payment order for purchase entries      |
| `idempotency_key`  | Retry-protection key when applicable    |
| `occurred_at`      | Accounting time                         |

Transaction types:

```
purchase
adjustment
reservation_hold
reservation_settlement
reservation_release
reservation_expiry
```

Important details:

- Rows are never updated or deleted by the runtime role.
- Corrections should be new ledger entries.
- A purchase must reference a payment order.
- A partial unique index ensures only one purchase transaction can exist for a payment order.
- `adjustment` exists in the domain model, but there is no application command or API that exposes it.

## 3.6 `billing.idempotency_records`

Prevents retries from performing a financial action twice.

| Field | Meaning |
| --------------------- | ------------------------------------------- |
| `scope`               | Operation, such as `reserve_credits`        |
| `namespace`           | Organization, reservation, or user boundary |
| `key`                 | Caller-supplied idempotency key             |
| `request_fingerprint` | SHA-256 fingerprint of material input       |
| `resource_type`       | Created resource type                       |
| `resource_id`         | Original resource ID                        |
| `created_at`          | First successful execution time             |

Behavior:

- Same key + same request returns the original result.
- Same key + different request returns an idempotency conflict.
- PostgreSQL advisory locks serialize simultaneous requests using the same tuple.
- A uniqueness constraint provides the final database safeguard.

Namespaces are:

| Operation | Namespace |
| ------------------- | --------------- |
| Reserve credits     | Organization ID |
| Settle reservation  | Reservation ID  |
| Release reservation | Reservation ID  |
| Create payment      | User ID         |


### PostgreSQL SQL — reconstructed from this document

```sql
CREATE TABLE billing.idempotency_records (
    scope TEXT NOT NULL,
    namespace TEXT NOT NULL,
    key TEXT NOT NULL,
    request_fingerprint TEXT NOT NULL,
    resource_type TEXT NOT NULL,
    resource_id TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT idempotency_records_unique_key
        UNIQUE (scope, namespace, key)
);
```

The source describes `request_fingerprint` as SHA-256 but does not say whether the migration stores it as hex text, binary `BYTEA`, or another representation.

An observation is either:

# 4. Credit operations

## Purchase

After authoritative payment confirmation:

```
available += purchased credits
reserved  unchanged
```

A `purchase` transaction is appended in the same database transaction.

The account is created automatically if this is the user’s first successful purchase.

## Reserve

For a maximum expected cost of `M`:

```
available -= M
reserved  += M
```

A `reservation_hold` ledger entry is appended.

The reservation fails if the user does not have enough available credit.

## Settle

If the actual cost is `A`, where `0 <= A <= M`:

```
reserved  -= M
available += M - A
```

The difference is returned to the user, and the total wallet balance falls by the actual cost `A`.

A `reservation_settlement` transaction is appended.

## Release

If the operation is cancelled:

```
reserved  -= M
available += M
```

No credit is spent. A `reservation_release` transaction is appended.

## Expire

If the operation never finishes before its deadline:

```
reserved  -= M
available += M
```

No credit is spent. A `reservation_expiry` transaction is appended.

The default reservation lifetime is 24 hours and is owned by server configuration. Callers cannot choose an expiration time.

## Expected HTTP errors

- `404`: entity or active package not found.
- `409`: insufficient credits, idempotency conflict, or invalid state transition.
- `422`: invalid credit amount or invalid settlement.
- `503`: authentication boundary, Account integration, or BehPardakht configuration unavailable.

# 6. Cross-module interface

Other backend modules should not call Billing’s persistence classes directly.

The supported public Billing interface exposes three commands:

```
reserve_credits
settle_reservation
release_reservation
```

Payment operations are not exposed through this cross-module public interface.

This is a good bounded-context rule: another module asks Billing to perform an operation, while Billing owns its ledger and transactions.

# 7. Payment flow in detail

## Step 1: Create local order

Billing:

1. Locks the payment idempotency key.
2. Reads and locks the selected active package.
3. Copies the package’s credits and rial price.
4. Creates the payment order.
5. Changes it to `pending`.
6. Schedules the first reconciliation for 30 seconds later.
7. Commits the order and idempotency record atomically.

## Step 2: Redirect browser

The browser goes to:

```
BehPardakht /payment/pay
```

The URL includes:

- `uid`
- amount
- public App ID
- return URL
- optional phone number
- payment gate `10`

The secret App Key is never included in the browser URL.

## Step 3: Receive callback

The callback:

- Is public.
- Is not cryptographically signed.
- Is stored once.
- Pulls reconciliation forward.
- Never adds credit.

## Step 4: Backend reconciliation

The reconciliation worker:

1. Claims due payments with `FOR UPDATE SKIP LOCKED`.
2. Gives the claim a two-minute lease and random claim token.
3. Calls authenticated `POST /payment/details`.
4. If the provider says `Idle` (`1`), calls `/payment/check`.
5. Calls `/payment/details` again.
6. Stores every normalized observation.
7. Applies the final result only if it still holds the valid claim.

Provider interpretation:

| StatusResult               |                               |
| -------------------------- | ----------------------------- |
| `1`                        | Still pending; retry          |
| `2`                        | Paid, if UID and amount match |
| `3`, `4`, `5`              | Failed                        |
| Unknown                    | Manual review                 |
| UID or amount mismatch     | Manual review                 |
| Repeated unresolved errors | Manual review                 |

Retries use exponential backoff:

```
30s → 60s → 120s → ... → maximum 15 minutes
```

The configured default retry ceiling is 10 attempts.

Only status `2`, with matching UID and amount, can add credits.

# 8. Concurrency and double-spend protection

The module uses several layers of protection:

- Credit-account rows are locked with `SELECT ... FOR UPDATE`.
- Reservation rows are locked before state transitions.
- Expiry locks accounts in sorted user-ID order.
- Expiry and reconciliation use bounded batches and `SKIP LOCKED`.
- Idempotency keys use PostgreSQL transaction advisory locks.
- Payment reconciliation uses leases and claim tokens.
- Stale workers cannot apply results after losing a claim.
- Purchase ledger entries are unique per payment order.
- Projection changes and ledger inserts share one transaction.
- Database checks prevent negative balances.
- Runtime privileges prevent ledger updates and deletes.

One known weakness is that ID generation opens a second database connection while a unit of work already owns a connection. Under full pool load, this could cause connection-pool starvation.

# 9. Background processes

Billing is designed to run three independent processes.

## Payment reconciliation worker

Default poll interval: 5 seconds.

Responsibilities:

- Claim due pending payments.
- Contact BehPardakht.
- Retry, pay, fail, or send to manual review.
- Isolate failures so one broken payment does not stop the batch.

## Reservation-expiry worker

Default poll interval: 60 seconds.

Responsibilities:

- Find expired active reservations.
- Return the held credits.
- Append expiry transactions.

It does not need provider credentials.

## Integrity scheduler

Runs daily at midnight in `Asia/Tehran`.

It uses the read-only `ark_auditor` database role and never repairs data. It emits an error-level structured log if it finds a mismatch.

The audit checks 15 conditions, including:

- Account balance versus latest ledger balance.
- Broken transaction chains.
- Reserved balance versus active reservations.
- Overdue active reservations.
- Reservation state and ledger inconsistencies.
- Orphan reservation transactions.
- Paid orders without exactly one purchase grant.
- Callback amount mismatches.
- Missing or conflicting provider observations.
- Payments requiring manual review.
- Broken idempotency references.
- Overdue reconciliation.
- An empty active package catalog.

# 10. Database roles

Billing uses three PostgreSQL roles.

| RolePurpose    |                                               |
| -------------- | --------------------------------------------- |
| `ark_migrator` | Create schemas, tables, functions, and grants |
| `ark_runtime`  | Run normal Billing operations                 |
| `ark_auditor`  | Read-only integrity checking                  |

The runtime role can update mutable projections such as:

- Credit accounts.
- Reservations.
- Payment orders.

It can insert, but not update or delete:

- Ledger transactions.
- Callback receipts.
- Reconciliation observations.
- Idempotency records.

The auditor can only select from Billing tables.

Existing databases must have `ark_auditor` provisioned before applying migration `20260823_0004`.

# 14. Production-readiness status

The branch’s readiness review identifies four release blockers.

## P1: Authentication and ownership

In production, all customer Billing routes return `503` because authentication is not integrated.

Outside production, callers can supply user IDs and fetch objects without owner checks. This creates an IDOR-style risk in any environment reachable by untrusted users.

The current Account branch defines `billing.view` in [permissions.yaml (line 36)]\(/C:/Users/AFE AI/PycharmProjects/ark/apps/backend/src/ark/modules/account/permissions.yaml:36), but that permission is not wired into the Billing router.

## P1: Organization-owner resolution

Billing defines an `OrganizationOwnerResolver` port, but the runtime injects an adapter that always raises `AccountsIntegrationUnavailable`.

Therefore, reservation creation cannot currently succeed through the real composition root.

## P1: Missing Business and actor attribution

Reservations store:

```
payer_user_id
organization_id
```

They do not store:

```
business_id
actor_user_id
```

Ledger transactions also lack explicit organization, Business, payer, and actor dimensions.

This prevents reliable cost attribution between Businesses belonging to the same organization.

## P1: Missing live PostgreSQL race tests in CI

Unit tests are strong, but required database concurrency scenarios are not exercised in CI:

- Two reservations racing to spend the same balance.
- Duplicate payment grants.
- Callback versus reconciliation.
- Settlement versus expiry.
- Concurrent idempotent requests.
- Stale reconciliation-worker fencing.

## Other important gaps

- ID allocation may starve the database pool.
- Histories have limits but no pagination.
- Mobile financial tables rely on wide horizontal scrolling.
- Some error/status changes lack ideal accessibility announcements.
- BehPardakht sandbox behavior has not been verified.
- Refund, chargeback, and manual-review operational procedures are missing.
- The Billing branch and current Account/Organization branches still need integration.
